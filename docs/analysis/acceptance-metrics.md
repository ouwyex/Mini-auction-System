# Метрики приёмки и готовности к релизу

## Применимость

Пороги ниже — предлагаемые критерии приёмки, а не текущие измеренные показатели. Существующий проект — Flask/SQLite demo без платёжного провайдера, фонового worker и метрик наблюдаемости; поэтому часть показателей можно подтвердить тестовой выборкой и SQL-инвариантами, а production SLO вводить только вместе с инфраструктурой. Для порогов надёжности использовать согласованное окно не менее 7 дней staging soak или достаточный объём операций (см. формулы).

## Функциональные метрики

| Метрика / формула | Порог приёмки | Как измерять |
|---|---:|---|
| Успешность обязательных E2E: пройденные обязательные сценарии / запущенные обязательные сценарии | 100% для release suite; 0 необъяснённых падений | E2E suite по [e2e-acceptance-plan.md](e2e-acceptance-plan.md), отдельно текущий и целевой профиль |
| Лишние принятые ставки без допустимого обеспечения: count(bids lacking valid hold at acceptance) | 0 | Проверка БД/событий после каждого сценария; для текущего приложения — наличие held deposit, без обещания полного покрытия цены |
| Критические неверные назначения победителя: число закрытий не по max bid/tie-break/approved eligibility | 0 | Повторная выборка всех bid rows и вычисление ожидаемого кандидата |
| Доля дефолтов, обработанных утверждённым потоком: default cases with recorded outcome / confirmed defaults | 100% | Журнал исполнения и события; метрика доступна только после реализации fulfillment |
| Доля случаев перехода к следующему кандидату с зафиксированными согласием, ценой, сроком и исходной ставкой | 100% | Сверка истории awards/offers и event log |
| Покрытие исходов закрытия: closed/unsold lots с единственным финальным исходом | 100% | SQL-инвариант по лотам и сущности исполнения |

## Надёжность и целостность операций

| Метрика / формула | Порог приёмки | Измерение |
|---|---:|---|
| Несанкционированные отрицательные доступные балансы | 0 случаев | SQL-проверка `users.balance >= 0`; целевую доступность считать с учётом reservations |
| Дублированные финансовые эффекты: повторные capture/release/refund на одну бизнес-операцию | 0 | Сверить idempotency key и ledger/event IDs после повторов и гонок |
| Идемпотентность закрытия/платёжного callback | 100% повторов без дополнительного эффекта | Повторить каждый запрос минимум 3 раза и отправить callback в обратном порядке; сравнить ledger и состояния |
| Успешность фиксации целостной транзакции (состояние + ledger + событие/outbox) | 100% либо безопасный rollback | Fault injection между шагами; после восстановления нет частичного результата |
| Доля необработанных/неизвестных статусов платежа, ошибочно превращённых в дефолт | 0 | Тест timeout, provider outage, delayed callback; аудит переходов |
| Время закрытия истёкшего лота | Предлагаемый p95 ≤ 60 секунд после `closes_at` в production | Разница между `closes_at` и `auction.closed`; текущая система закрывает только при запросе, поэтому без worker это не гарантируется |
| Время обработки согласованного дефолта и запуска следующего предложения | Предлагаемый p95 ≤ 60 секунд после deadline | `award.defaulted` → `award.offered_to_next`; нужен scheduler/worker |

## Консистентность данных и денежная сверка

Определения для внутреннего ledger:

- `ledger_balance(user) = opening_balance + Σ(wallet_transactions.amount)`.
- `available(user) = wallet_balance − Σ(active_reservations)` (если введены резервы).
- `reserved_total(lot/user)` должен совпадать с действующими reservation rows и ожидаемой максимальной ставкой согласно утверждённой модели.
- Для каждого лота одновременно может существовать не более одного текущего award holder; история первоначального победителя сохраняется при переходе.
- `held deposit` на активном/ожидающем лоте либо существует как ровно один депозит на user/lot, либо получает явное терминальное состояние при settlement.

| Метрика / формула | Порог приёмки | Измерение |
|---|---:|---|
| Ошибка ledger: `abs(balance − ledger_balance)` | 0.00 для каждого пользователя | SQL/Python reconciliation по каждому user после каждого E2E набора и ежедневно |
| Несовпавшие активные резервы | 0 строк | Сверка reservation ledger с текущими лидирующими/обязательными ставками |
| Незавершённые/двойные исходы лота | 0 | Инвариант: максимум один действующий holder, ровно один terminal outcome |
| Денежные записи без lot/correlation/idempotency ссылки в торговом потоке | 0 | Проверка полноты обязательных полей события/ledger |
| Частичные операции после fault injection | 0 | Проверки согласованности после принудительного rollback и перезапуска |

Для текущей схемы `REAL` и нет таблицы резерва; сравнение ledger возможно, но гарантия денежной точности для реальных платежей отсутствует. Для реального запуска требуется целочисленное хранение минимальных единиц валюты и формальная сверка с внешним провайдером.

## Бизнес-метрики

Метрики не заменяют контрольные инварианты и не являются основанием автоматически наказывать пользователей.

| Метрика / формула | Целевой порог на пилоте | Как интерпретировать |
|---|---:|---|
| Доля неисполнения: подтверждённые победители, не завершившие оплату в срок / все подтверждённые победители | ≤ 2% после минимум 100 закрытий; до этого только мониторинг | Если выше — проверить обеспечение, UX, сбои провайдера и реалистичность срока |
| Успешность перехода: лоты, где следующий кандидат завершил сделку / лоты, предложенные следующему кандидату | ≥ 50% после минимум 30 предложений; диагностическая цель | Низкое значение требует анализа цены предложения и задержки, не автоматического усиления штрафа |
| Возвраты/освобождения в срок: завершённые non-winning holds, обработанные в согласованный SLA / все такие holds | ≥ 99.5%, целевое 100% | Проверять ledger и время закрытия/исхода |
| Доля споров/обращений по санкциям: обращения, связанные с дефолтом/ограничением / подтверждённые дефолты | < 5% после минимум 100 дефолтов | Метрика требует канала обращений; проверять ложные дефолты и ясность условий |
| Конверсия участия: уникальные пользователи с принятой ставкой / уникальные пользователи, открывшие форму ставки | Отслеживать до утверждения baseline, не задавать release gate | Сильное падение после введения полного обеспечения может означать несоответствие UX/лимитов |

Пороговые бизнес-цели являются первоначальными гипотезами и должны быть пересмотрены после пилота; при малых выборках показывать абсолютные числа и доверительный интервал, не трактовать процент как стабильный.

## Приёмка наблюдаемости

- Для каждого действия сохраняются UTC timestamp, lot/user, correlation и idempotency keys; секреты и платёжные реквизиты исключены.
- Дашборд/отчёт разделяет технический отказ, недостаток средств до ставки, отказ оплаты и просрочку; эти причины не сводятся в один «штрафной» показатель.
- Есть сигнал при любом нарушении финансового инварианта, двойном capture, двух действующих получателях права или отсутствии обработанного закрытия дольше порога.
- Операционный процесс умеет сверить pending платежи и исправить результат с обязательной audit-записью.

## Ограничения текущей готовности

Существующие тесты проверяют 10% депозит, отказ ставки без депозита, победителя по максимальной ставке и возврат других депозитов, но не тестируют нехватку денег победителя после закрытия, завершение покупки, дефолт, санкцию или передачу права следующему. Текущая схема не содержит данных, необходимых для большинства целевых метрик. Поэтому приёмку функционала «санкции и переход права» нельзя объявить успешной только по существующему тестовому набору; сначала нужны согласованные правила и реализация.
