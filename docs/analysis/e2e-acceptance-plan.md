# План сквозной приёмки

## Область

План проверяет текущие потоки ставок, депозитов, закрытия и рекомендуемый будущий поток исполнения/дефолта. Метка **Текущий** означает проверяемое требование существующей реализации; **Целевой** — сценарий приёмки после отдельной реализации правил из [deposit-penalties.md](deposit-penalties.md). Целевые сценарии не являются утверждением, что соответствующий функционал существует.

### Компоненты

| Обозначение | Компонент |
|---|---|
| UI | `templates/lot_detail.html`, `wallet.html`, `my_bids.html`, `notifications.html` |
| HTTP | Flask routes и `prepare_request()` в `app.py` |
| Auction | `winning_bid()`, `close_expired_lots()`, проверка/запись ставки, soft-close в `app.py` |
| Wallet | `wallet.py`: расчёт/списание депозита, ledger, возврат и settlement |
| DB | `schema.sql`, `db.py`, SQLite-транзакции, ограничения и индексы |
| Notice | `notifications.py` и таблица `notifications` |
| Fulfillment (целевой) | Будущая сущность состояния сделки/назначения и обработчик срока оплаты |
| Audit (целевой) | Будущий журнал доменных событий/transactional outbox |
| Provider (целевой) | Будущая интеграция авторизации/списания, если используются реальные платежи |

## Подготовка среды

- Изолированная тестовая БД по текущей `schema.sql`; пользователи продавец, участники A/B/C и администратор.
- Управляемые часы либо установка `closes_at` относительно UTC; фиксированная тестовая валюта и точность до 0,01.
- Для целевых сценариев: включённая политика обеспечения, настраиваемый срок оплаты, тестовый провайдер с исходами success/failure/timeout/duplicate callback; часы позволяют продвинуться за deadline.
- Снимать состояние до и после: `lots`, `bids`, `deposits`, `users.balance`, `wallet_transactions`, уведомления; целевое — резервы, fulfillment, ограничения аккаунтов и audit/outbox.
- Каждый финансовый сценарий повторять с повторным запросом и конкурентным запросом, если это указано.

## Сценарии

|---|---|---|---|
| A01 Позитивный: внести депозит | Активный чужой лот, цена старта 100, баланс 100; авторизованный user отправляет депозит | Списано 10,00; одна запись `held`, одна `deposit_paid`; баланс 90; UI показывает допуск к ставке | UI, HTTP, Wallet, DB — Текущий |
| A02 Позитивный: ставка с депозитом | Есть held-депозит; подать минимальную допустимую ставку | Одна ставка записана, цена/лидер обновлены; транзакция консистентна; прежний лидер получает outbid notice при смене лидера | HTTP, Auction, DB, Notice — Текущий |
| A03 Позитивный: закрытие лота | У A и B held-депозиты, ставки 100 и 105, время истекло; вызвать любой запрос | Лот `closed`; выигрывает B; B deposit `applied`, A `returned`, возврат отражён в ledger ровно один раз | Auction, Wallet, DB — Текущий |
| A04 Граница: равные ставки | Две валидные равные ставки; первая записана раньше | Более ранняя ставка — победитель; результат одинаков при повторном чтении | Auction, DB — Текущий |
| A05 Граница: ставка на soft-close | Ставка в последние 30 секунд | Срок продлён на 2 минуты согласно текущему правилу; не закрыть лот до нового срока | Auction, DB — Текущий |
| A06 Позитивный: следующее право | Лот завершён; победитель не оплатил; B следующая допустимая ставка согласна принять предложение по утверждённой цене | Первоначальный исход сохранён; A помечен defaulted; B становится текущим кандидатом только после принятия; точная цена и deadline зафиксированы; seller/both candidates notified по политике | Fulfillment, Auction, Notice, Audit — Целевой |
| A07 Негативный: недостаточно средств до ставки | Доступный остаток меньше требуемого обеспечения; отправить ставку | Ставка отклонена; лидер/цена/остаток/резервы неизменны; UI показывает нужную и доступную сумму; санкция не создаётся | UI, HTTP, Wallet/hold, DB — Текущий вариант отсутствует; Целевой |
| A08 Негативный: отсутствует депозит | Нет held-депозита; отправить ставку | Текущая система отклоняет её и не создаёт bid; пользователь видит сообщение внести депозит | HTTP, Auction, DB, UI — Текущий |
| A09 Негативный: победитель не оплатил | Победитель ожидает оплаты; время превышает deadline, провайдер не имеет pending результата | Идемпотентно записан дефолт с причиной; применена только утверждённая политика денег; событие и уведомления созданы; начато предложение следующему | Fulfillment, Provider, Audit, Notice — Целевой |
| A10 Граница: платёж pending/timeout | Провайдер не дал окончательный ответ к deadline или запрос истёк | Не назначать дефолт и не передавать право до сверки; оставить `payment_pending`/reconciliation; повторы безопасны | Provider, Fulfillment, Audit — Целевой |
| A11 Граница: дубли/гонка закрытия | Два запроса закрытия, два одинаковых callback или повтор POST ставки | Одна запись исхода/списания/возврата и один переход кандидата; повтор возвращает ранее известный результат | Auction, DB, Provider, Audit — Целевой |
| A12 Граница: исчерпана очередь | Все участники после победителя отказались/не оплатили | Лот получает согласованный исход `unfulfilled`; никто не отображается победителем без принятия; все свободные резервы обработаны однократно | Fulfillment, Wallet, UI, Audit — Целевой |
| A13 Негативный: ограниченный аккаунт | Аккаунт имеет активное ограничение ставок | Новая ставка запрещена с кодом/сообщением и сроком ограничения; существующие операции просмотра/оплаты остаются доступными по политике | HTTP, Account policy, DB, UI — Целевой |
| A14 Граница: технический отказ не штраф | Платёжный сервис временно недоступен либо вернул неизвестный статус | Нет `defaulted`, штрафа и санкции; операция остаётся на сверке; продавец видит корректный статус ожидания | Provider, Fulfillment, Audit, Notice — Целевой |
| A15 Негативный: чужой/закрытый лот | Запрос депозита/ставки от продавца на свой лот или по уже закрытому лоту | Отказ без изменения денег/ставок; корректный HTTP/сообщение | HTTP, Auction, Wallet — Текущий |
| A16 Позитивный: отмена/unsold/swap | Отмена лота, лот без ставок либо принят item swap при наличии held депозитов | Нет наказания участникам; возврат каждого held депозита ровно один раз; при swap нет денежного победителя | HTTP, Auction, Wallet, Swaps, DB — Текущий |
| A17 Консистентность ledger | Несколько депозитов, возвратов и пополнений; сверить баланс с историей | Для каждого пользователя balance равен начальному балансу + сумме операций; `balance_after` совпадает с порядком ledger; отрицательного баланса нет | Wallet, DB — Текущий; резервы — Целевой |
| A18 Аудит и объяснимость | Ставка отклонена, дефолт, передача кандидату и ручная отмена | Для каждого действия есть actor/time/lot/correlation/reason; можно восстановить исходную очередь и все денежные переходы; секретов оплаты нет | Audit, Admin — Целевой |

## Выходные критерии

- Все сценарии Текущего объёма проходят на поддерживаемой схеме и не противоречат текущим правилам README.
- Целевые сценарии A06–A14 и A18 остаются заблокированы для приёмки до утверждения параметров и реализации; для релиза, заявляющего поддержку исполнения/санкций, они обязательны.
- Нет необъяснимого расхождения денег, повторного захвата/возврата, двух победителей или передачи права при неопределённом статусе оплаты.
- Любой отказ сопровождается стабильным кодом, безопасным пользовательским сообщением и неизменностью несвязанных данных.

## Открытые решения

Согласовать: обеспечение (полное/10%/авторизация), применение депозита к цене, финальную цену следующему участнику, сроки оплаты и принятия предложения, разрешённые причины снятия с очереди, удержание залога/штраф, пороги и сроки ограничений, ручные действия администратора, платёжный провайдер, режим обработки просрочки и поддерживаемые валюты.
